# 開発方針とロードマップ

## 設計上の決定事項

### 第3階層の選定基準（確定）
第3階層は「中心都市の点」とし、次の規則の和集合とする。

| 規則 | 内容 |
|---|---|
| R1 | 国の首都 |
| R2 | 第2階層ごとの首府（州都・県庁所在地・レジオン首府）。ドイツの都市州は都市自体を首府とする |
| R2′ | 首府を持たない第2階層（英イングランドの地域区分）は、地域内で FUA 人口が最大の都市を代表都市とする |
| R3 | FUA 人口が 100 万以上、または国内の FUA 人口上位 20 都市の中心都市 |

- 規則に該当する都市を Tier A、該当しないが国別の学習価値がある都市（日本の中核市など）を Tier B（補助枠）とする。クイズの出題は Tier A のみ。地図上では Tier B を控えめに描画する。
- 実装：元データ（`src/data/countries`）は書き換えず、選定レイヤー（`src/data/selection`）で首都・首府・FUA 代表を指定し、`applySelection` で tier・基準・都市圏人口を導出する。選定対象の FUA は `data-src/fua-attributes.json` から `bun scripts/select-fua.ts` で自動抽出する。
- 特記事項：GHSL の FUA 名には国境をまたぐものがあり、「Tijuana」（米側＝サンディエゴ）と「Detroit」（加側＝ウィンザー）は実体の都市に読み替えた。「Mestre」はヴェネツィア本土部で、ヴェネツィアのコムーネに含まれるため、ヴェネツィアが代表する。ワシントンD.C.は連邦区として第2階層に追加した（Natural Earth のポリゴン）。
- 基準の限界：閾値は便宜的であること、FUA 人口は 2015 年の推計値で国勢調査と一致しないこと、首府の選定は制度に基づき機能上の中心性と一致しない場合があること、を画面にも明記する。

### 都市圏比較機能（実装済み）
- 画面：ヘッダーの「都市圏比較」、または第3階層の詳細パネルの「この都市圏を、他と同じ縮尺で比べる」から開く。最大4件を、同縮尺で「重ねる」「並べる」。人口・面積・人口密度・順位のカードと、169件の一覧表（並べ替え・国別の絞り込み・検索）を備える。
- 投影：各都市圏の重心を中心とする正積方位図法（単位 km）。全都市圏が同縮尺で、面積も保たれる。
- 境界データ：`public/data/fua.json`（388 件、1,094 KB、gzip 約 245 KB）。`scripts/extract-fua-geometry.py` で、GHS-FUA の GeoPackage から再生成できる（許容誤差 0.004 度、座標は小数 3 桁）。比較画面を開くまで読み込まない。
- 整合の検査：境界の面積が属性表と 3% 以内であること、選定 FUA と 1 対 1 であること、容量が 1,200 KB 以内であることを、`bun run validate` と単体テストで確認する（実測では、全件が 1% 以内）。
- 定義の記述は、GHSL の解説資料（JRC, 2019）に基づく。GHS-FUA は通勤の実測ではなく、OECD 諸国の実際の FUA で学習した統計モデルによる推定で、隣接する都市圏は統合される。
- 階層学習・クイズとは分離した独立機能とする。
- データ：GHSL の GHS-FUA R2019A（基準年 2015）。ライセンスは CC BY 4.0。出典の明記と、改変（投影変換・簡略化）の明示が必要。
  - 取得元：`https://jeodpp.jrc.ec.europa.eu/ftp/jrc-opendata/GHSL/GHS_FUA_UCDB2015_GLOBE_R2019A/V1-0/`
  - 属性：FUA 人口・面積、中心域（UC）人口・面積、通勤圏人口、国コード。
  - 規模：対象国の全件を簡略化（許容誤差 0.01 度）して約 1.2 MB（gzip 約 0.37 MB）。人口上位約 100 件なら約 0.4 MB。
- 留意点：人口は 1 km 格子からの推計、複合都市は 1 件に統合されている（例：ライン・ルール）、各国の公式な都市圏定義とは一致しない。

### 対象国の拡張（中国・インド）（実装済み）
- 境界：Natural Earth の admin-1（中国 31、インド 36）。係争地域の描画は Natural Earth の標準に従い、独自の判断は加えていない。台湾・香港・マカオは収録しない。
- 第1階層：中国は 7 大区、インドは地域評議会（Zonal Council）の 6 区分。いずれも慣習的区分で、公式の統計区分ではない。
- 統計：中国は 2020 年国勢調査、インドは 2011 年国勢調査（`statistics.json`）。出典の取得経路と留意点は、他国と同じ。
- 第3階層：同じ基準（R1・R2・R3）を適用。中国 111 都市、インド 104 都市（いずれも Tier A のみ）。
- GHSL の分割・命名の癖への対処：珠江デルタが「Guangzhou」の名で 8 つに分割されているなど、独立した中心都市を持たない断片、市轄区、同定できない地方行政中心は、`data-src/fua-exclusions.json` に理由を記して除外した（中国 7、インド 2）。除外を先に適用してから、国内上位 20 を数える。
- 代表都市の同定：FUA の名称ではなく、既知の都市の座標がどの FUA に含まれるかで確認した（例：「Faizabad」＝アヨーディヤー、「Ettumanoor」＝コッタヤム、「Tianjia'an」＝淮南）。代表都市の座標は、すべて対応する FUA の境界内にあることを確認済み。
- 共同首府：インドのパンジャーブ州・ハリヤーナー州の首府は、連邦直轄領のチャンディーガル。`sharedCapitals` で表す。
- アーンドラ・プラデーシュ州の首府は、アマラヴァティ（新首都を建設中。州都の位置づけには経緯がある）。ジャンムー・カシミールは、夏の首府シュリーナガルを代表とし、冬の首府ジャンムーも収録している。

### 韓国（実装済み）
- 作成時（Gemini）に含まれていた韓国を、他国と同じ基準で再構築した。第2階層は、**2026年7月1日に光州広域市と全羅南道が統合して「全南光州統合特別市」となったため、17ではなく現行の16**。境界は、2018年基準の2つの境界を結合した（不正なリング 15 件も除去）。代表都市は光州（庁舎が順天・務安郡・光州市西区に分かれるため、首府ではなく、域内で都市圏人口が最大の都市 = R2p）。
- 第1階層は、6つの慣習的な広域圏（首都圏・江原圏・忠清圏・湖南圏・嶺南圏・済州圏）。
- 第3階層：26 都市（道庁所在地16と、都市圏人口の上位の都市）。首府が複数ある道（京畿道：水原・議政府、慶尚北道：安東・浦項、慶尚南道：昌原・晋州）は、最初に挙げた都市を首府とし、他は庁舎の所在として記す。忠清南道は、洪城郡（内浦新都市）。
- 統計：2020 年人口住宅総調査（統計庁）。面積は行政安全部。
- GHSL の FUA は、20 件すべてが都市と 1 対 1 に対応し、除外は不要だった（ソウル圏に仁川・水原・城南・高陽、大田に世宗、釜山に金海が含まれることを、座標で確認済み）。

## 統計データの扱い
- 第2階層の人口・面積は `src/data/statistics.json` に、出典 ID・基準日・面積の基準（総面積／土地面積）とともに保持する。`applyStatistics` が元データの概数を置き換え、広域区分（第1階層）の人口は所属する第2階層の合計から導出する。
- 基準年は国により異なる（日本・米国2020、カナダ2021、英国2021／2025、仏2022、独2023、伊2026）。
- 取得経路は Wikipedia の統計表（脚注が各統計機関の資料を参照）。一次資料での再照合は未実施であり、`statistics.json` の `via` に明記している。
- 従来の概数との差は、人口では 172 件中 2 件（カナダのプリンスエドワードアイランドとアルバータ）のみ 10% を超え、面積では 10% を超えるものはなかった。

## フォント（Phase 6）
- 従来は、`index.html` が Google Fonts（Cinzel、Plus Jakarta Sans、Noto Sans JP）を読み込んでいたが、CSS のどこにも適用されておらず、外部通信だけが発生していた。読み込みを削除した。
- 本文は Noto Sans JP（SIL OFL 1.1）を、`@fontsource/noto-sans-jp` で自前配信する。太さは 400 と 700 のみ（500 は 400、600・800 は 700 に寄せて表示される）。
- 字種ごとに分割（unicode-range）されており、ブラウザは必要な範囲だけを取得する。実測では、初回表示で woff2 を 53 枚・約 640 KB、都市圏比較を開くと、さらに 47 枚を取得する。ビルド成果物（dist）には、全スライスの woff2（約 8 MB）が含まれる。
- 旧形式（woff）は、`vite.config.ts` のプラグインで取り除いている。
- さらに軽くしたい場合は、使われている文字だけに絞った単一のサブセットを作る方法がある（ただし、元のフォントファイルが別途必要）。

## 地図まわりの構造（Phase 3）
- `src/components/MapCanvas.tsx` は合成のみ。責務は `src/components/map/` のフック・部品に分けた（地図の生成と移動 `useLeafletMap`、GeoJSON 取得 `useGeoJson`、多角形 `usePolygonLayer`、マーカー `useMarkerLayers`、ラベルの重なり回避 `useLabelVisibility`、操作部品 `MapControls`・`MapHud`）。
- GeoJSON 地物と第2階層の照合は、`src/utils/featureMatching.ts` の完全一致のみ（従来の部分一致は廃止）。検証スクリプトも同じ関数を使うため、「検証が通る＝アプリで照合できる」が保証される。
- ラベルは、画面座標で重なりを判定し、優先度の低い方を隠す（首都 > 首府 > 都市圏の中心都市 > 補助枠。選択中は常に表示）。点と、ホバー時の説明は常に残る。
- イベントハンドラは最新値を参照する ref 経由にし、親の再描画でマーカーを作り直さないようにした。
- バンドル：初期表示に不要なモーダルとクイズを遅延読み込みにし、leaflet・react を別チャンクに分けた（未使用の d3 投影コードと各国の `projectionConfig` は削除）。
- モバイル：ヘッダーと操作部をアイコン中心に縮め、詳細パネルは小画面で下部のシートにした。小画面では二言語表記を既定で無効にする。

## データ検証
```bash
bun run validate   # データの整合性
bun run test       # 単体テスト（vitest）
```
親子関係、ID 重複、広域区分と第2階層の整合、GeoJSON と第2階層の 1 対 1 対応、座標範囲を検査する。CI（`deploy.yml`）でも実行される。
